Project overview

simcore owns a heterogeneous set of simulation entities, advances simulated time in fixed steps, and lets callers iterate entities by concrete type. It is a library, not an application: it does not define what a particle, sensor, or vehicle is, and it does not provide rendering, networking, persistence, or domain rules. A consumer supplies entity types with a single void update(double dt) member, links the library, and keeps its simulation code in its own files. The repository includes several consumers, a test suite, and documentation, but the core remains independent of any one simulation.

Architecture at a glance

Entities are stored behind a type-erased base, while the public API remains typed. Updates are deterministic, removal is deferred until the active pass ends, and events are delivered after all entities have run for a step.

Consumer types

User-defined structs such as Particle and Thermometer. The only requirement is update(double).

Registry

Heterogeneous slots, type-erased ownership, generation-tagged IDs, deferred despawn, and typed views.

Stepper

Fixed-step run and step, priority order, final remainder, event dispatch.

View of T

Slot-index traversal, exact type filter, O(N) in total slots, safe during deferred removal.

EventBus

Typed subscribe and publish. Delivery is queued and happens at the end of a step.

Lifetime and safety

  • EntityHandle<T> stores a weak reference, the owning registry, and a packed index plus generation ID.
  • A stale handle resolves to null after its slot is released, and a mismatched type is rejected by a runtime type check.
  • despawn marks the entity dead immediately but releases storage only when the current update pass or view traversal ends.

Execution model

  • One registry is single-threaded and not thread-safe; all access happens on one thread.
  • Lower priority numbers update first; equal priorities keep registration order.
  • Events published during a step are delivered after every entity has updated.

Quick start

The Windows MinGW configuration is the one verified in this repository. From the repository root, use these three commands:

cmake -S . -B build -G "MinGW Makefiles" -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release
ctest --test-dir build -C Release --output-on-failure

The README also contains a Linux and macOS block. Only the Windows block above was executed for the measurements on this page. The demo is build\examples\simcore_demo.exe on Windows.

What the 36 cases cover

  • 17 stepper cases: fixed steps, final remainder, explicit steps, accumulator behavior, priority order, and deferred self-despawn.
  • 8 registry cases: coexisting types, despawn during traversal, stale-handle idempotence, batch creation, and batch removal.
  • 4 entity-handle cases: identity, owning-registry equality, stable hashing, and use as an unordered-map key.
  • 6 event-bus cases: deferred delivery, type filtering, listener order, unsubscribe, and listener-published events.
  • 1 compile-failure case: a type without update(double) must be rejected by the Entity concept.

Known limitations

Documentation build: cmake --build build --target doc currently exits with an error at include/simcore/registry.h:136. The non-Entity overload of spawn_many lacks @param and @return tags, so Doxygen's strict mode stops before writing build/docs/html/index.html. The fix is to document that overload; library behavior is unaffected.
  • Packaging: consumers use add_subdirectory and link simcore::simcore. There are no install or export rules, so find_package(simcore) is not supported yet.
  • Team process: only three of six contributors reach 8 commits, only one contributor reaches 2 pull requests, and no pull request has a review from another person. The commit span is 10 days (2026-11-17 to 2026-11-27), below the rubric's 70% target for the eight-week example.
  • Stale supporting material: docs/slides.pptx and docs/speech.md predate the 36-case suite. Use docs/Group10_simcore_Presentation.pptx, this page, and docs/qa.md for current numbers.
  • Presentation length: D8 asks for at most 10 slides. The current group deck has 15 slides, while the original 10-slide deck predates the current test suite. The group must trim the current deck or refresh the 10-slide deck before submission.
  • Threading: a Registry and its EventBus are single-threaded and not thread-safe. Separate registries can be used on separate threads, but one registry must not be shared concurrently.
  • Platform coverage: only the Windows MinGW build was executed for the measurements here. The Linux and macOS command block in the README has not been verified in this environment.
  • Live demonstration: the live entity-addition sequence is scripted and rehearsed, but the classroom run is the remaining step.

The GitHub repository link requires network access. Every other link on this page is relative to the repository root and works from a local copy.
